# Franken-E58 Phase 1, Module 5: LittleFS, Wi-Fi AP, static pages, IMU under Wi-Fi

**Scope:** a read-only LittleFS mount (`components/hal_fs`), a Wi-Fi soft-AP and a static file server (`components/comms`: `wifi_ap`, `http_static`), web content built from `web/` into `data/`, an HTTP client for the laptop, and an early check of the 1 kHz IMU loop on Core 1 while Wi-Fi runs on Core 0 (blueprint risk R5). The joystick UI, nippleJS and the `/ws` WebSocket are not part of M5.

Blueprint sections used: §3.4, §4.2, §4.6, §4.9, §4.10, Phase 1 M5, risks R4 and R5.

**Status: M5 passed** (bench run of 2 November 2026, §8). Blueprint revision 2.8 records the results.

**Credentials:** copy `components/comms/include/wifi_credentials.example.h` to `wifi_credentials.h` in the same folder (git-ignored) and set your own SSID and password there; the build stops with a pointer to the template if the file is missing.

### Part 1: components
- **`hal_fs`:** mounts LittleFS from partition `storage` (subtype spiffs) at `/fs`, **read-only**, no format on failure, no grow. Reports total and used bytes (`esp_littlefs_info`). Reads use the cache-mapped partition (`CONFIG_LITTLEFS_MMAP_PARTITION`).
- **LittleFS source:** `joltwallet/littlefs` pinned `==1.22.3`, declared in `components/hal_fs/idf_component.yml`, resolved by the IDF component manager into `managed_components/` and locked in `dependencies.lock` (committed).
- **`comms::wifi_ap`** (esp_wifi, esp_netif): soft-AP on `board::kWifiChannel` (1), WPA2-PSK, `max_connection` 1, HT20, `WIFI_PS_NONE`, 802.11 b/g/n, 192.168.4.1 with the default DHCP server, `WIFI_STORAGE_RAM`. Records the time from `esp_wifi_start()` to `WIFI_EVENT_AP_START` and station joins and leaves (seqlock written by the event handler).
- **`comms::http_static`** (esp_http_server): GET only. `/` serves `index.html`. Files are stored as `<name>.gz` and sent with `Content-Encoding: gzip` and the Content-Type of `<name>`. Paths containing `..` get 400, unknown paths 404, other methods 405 (httpd's own method check). `/version` returns the firmware's compile-time version as JSON. `/ws` is reserved for M6 (404). Files are sent in 2 KB chunks from one static buffer. Server task pinned to Core 0 (`core_id = 0`), `TCP_NODELAY` on every socket (open callback), LRU purge on.
- **Web content:** `web/index.html` (placeholder "Franken-E58 M5", fetches `/version`). `tools/build_web.py` gzips `web/` into `data/` and generates `test.bin`: 102 400 bytes of fixed-seed xorshift32 output (incompressible, about 100 KB after gzip), SHA-256 `7af9066e2203ce56913f6f3f2bca595575034c277d69529b8c1a982500a002c5`.

### Runtime flash writes and how they are disabled

| Path that could write flash after boot | Default | M5 setting |
|---|---|---|
| PHY calibration data stored in NVS (first boot, or invalid data) | `CONFIG_ESP_PHY_CALIBRATION_AND_DATA_STORAGE=y` | `n`: full calibration at every boot, never stored. `esp_phy_store_cal_data_to_nvs` is not linked |
| Wi-Fi configuration in NVS | `CONFIG_ESP_WIFI_NVS_ENABLED=y`, storage `WIFI_STORAGE_FLASH` | `n`, `init.nvs_enable = 0` and `esp_wifi_set_storage(WIFI_STORAGE_RAM)` |
| `nvs_flash_init()` (can erase and initialise pages) | n/a | Never called, and not linked. The Wi-Fi OS adapter still links `nvs_open`, `nvs_set_blob` and `nvs_commit` through its function table, but they are used only with `nvs_enable` set and would fail on an uninitialised NVS |
| LittleFS writes | n/a | Read-only mount (`ESP_VFS_FLAG_READONLY_FS`), never formats, never grows, plus the partition `readonly` flag: `esp_partition_write` and `esp_partition_erase_range` return an error (IDF `partition_target.c`) |
| Core dump to flash | n/a | Already `CONFIG_ESP_COREDUMP_ENABLE_TO_NONE` |

### Bench test (`src/m5_wifi_test.cpp`, `FE_M5_TEST`)
`FE_M5_TEST` is mutually exclusive with `FE_M2_TEST`, `FE_M3_TEST` and `FE_M4_TEST` (compile-time `#error`). `FE_IMU_ISR_INSTRUMENT` is on for M3, M4 or M5. Everything prints from Core 0; Core 1 stays silent.
1. Mount the filesystem: `SUMMARY FS` (total, used, free).
2. Start the AP: `SUMMARY AP` (channel, authmode, max connections, power save, bandwidth, protocol, start-up time, internal heap before and after, minimum free). Station joins and leaves are printed throughout.
3. Start the HTTP server: `SUMMARY HTTP`.
4. **M5-IMU-1**, 300 s, AP up with no client: M3 Phase B on Core 1, started after the AP is up. One second in, `SUMMARY TASKS` checks the core of `wifi`, `tiT`, `httpd`, `sys_evt`, `esp_timer`, `m5_test`, `m3_report` (Core 0) and `imu` (Core 1) by task name (`xTaskGetHandle`, `xTaskGetCoreID`). Internal heap every 10 s.
5. Prompt to join the laptop; wait up to 300 s for a station; 5 s settle; idle heap reference; prompt to start `python3 tools/m5_http_test.py --load 330`; wait (up to 120 s) for the first request.
6. **M5-IMU-2**, 300 s under that load, internal heap every 10 s.
7. Wait until no request has arrived for 10 s, then `SUMMARY HEAP` (idle against after-load, minimum free, request counters), the recap block, and a heap line every 60 s while the AP and page stay up.

Each IMU SUMMARY line gives interval sd, jitter, wake min/avg/max, burst avg/max, missed, timeouts and I2C errors against the M3 baseline (interval sd 0.44 µs, jitter 3.7 µs, wake 6/7.0/12 µs, burst average 450.4 µs, zero missed), the acceptance 8 verdicts, the HTTP requests served during the run, and an **R5** field naming any figure worse than the baseline by more than the spread seen between the M3 and M4 runs (sd +0.1 µs, jitter +1 µs, wake max +4 µs, burst average +1 µs).

### Client (`tools/m5_http_test.py`, standard library only)
- Default: GET `/` 200 times (success count, min/avg/max latency); GET `/test.bin` 20 times (length and SHA-256 after gzip decoding, throughput); `/no-such-file` 404, POST `/` and PUT `/index.html` 405, `/../index.html` and `/a/../index.html` 400, `/ws` 404, `/version` 200.
- `--load SECONDS`: GET `/` every 50 ms and `/test.bin` every 2 s.
- Prints one summary block with PASS or FAIL.

## 2. Decisions

| ID | Decision | Reason |
|---|---|---|
| D-M5-01 | LittleFS from the pinned managed component `joltwallet/littlefs ==1.22.3`; `dependencies.lock` committed, `managed_components/` ignored | User decision (route a). Needs network at the first CMake configure and whenever `managed_components/` is missing; offline afterwards |
| D-M5-02 | Manifest in `components/hal_fs/idf_component.yml` rather than `src/` | The dependency belongs to the component that uses it. Deviation from the M5 plan wording |
| D-M5-03 | Read-only mount plus the partition `readonly` flag | No flash writes from the start (R4). `uploadfs` is unaffected: esptool writes raw flash at `$FS_START` and never reads the partition table |
| D-M5-04 | `CONFIG_LITTLEFS_MMAP_PARTITION=y` | Without it every LittleFS read goes through `esp_flash_read()`, which disables the cache on both cores (`spi_flash_os_func_app.c`) and would stall flash-resident code on Core 1 while pages are served |
| D-M5-05 | No NVS at all: Wi-Fi NVS off, PHY calibration not stored, `nvs_flash_init()` never called | Stricter than the spec, which allowed NVS init at boot. Cost: full PHY calibration at every boot |
| D-M5-06 | `GET /version` (JSON from `esp_app_get_description()`) | A static LittleFS page cannot know the firmware version. Approved deviation from "files only" |
| D-M5-07 | `..` in a path returns 400 | The spec says "reject" without a code |
| D-M5-08 | M3 Phase B can run again on the same tasks (`m3_phase_b_start()` after `m3_phase_b_result()`); the Core 1 task polls an atomic flag between runs | Two runs per boot. The task notification belongs to the data-ready ISR, so it is not reused |
| D-M5-09 | No "second device refused" line | IDF 5.5.3 raises no event for an association refused at `max_connection` (soft-AP events: start, stop, station connected, disconnected, probe request, wrong password). What the second device shows is recorded by hand |
| D-M5-10 | Acceptance 6 idle reference: internal free heap with the AP up, the laptop joined, before the load starts | Joining a station itself costs heap, so the reference must include it |
| D-M5-11 | Footprint compared with the M4 build | M1 recorded no footprint figures |
| D-M5-12 | Test file of incompressible deterministic bytes | So the gzip-stored file is really about 100 KB on the wire and the throughput figure means something |

## 3. Acceptance criteria
1. Clean build; `tools/verify_sdkconfig.sh` passes, including the new Wi-Fi, PHY and LittleFS options.
2. LittleFS mounts read-only; total and used bytes reported.
3. AP on channel 1 with WPA2, HT20, one station maximum and power save off, confirmed by the log and by an external scan on the laptop.
4. A phone browser opens http://192.168.4.1 and shows the placeholder page with the firmware version; the 404, 405 and `..` cases behave.
5. Python client: 200 of 200 GET `/` succeed, the test file checksum matches 20 of 20 times, throughput and latency reported.
6. Internal free heap, after the load stops, is within 2 KB of the idle level with the AP up (no leak over about 1000 requests); minimum free heap reported.
7. Wi-Fi, lwIP and httpd tasks verified on Core 0.
8. IMU under Wi-Fi: zero missed samples, zero I2C errors, interval sd below 2 µs, jitter below 20 µs, wake max below 50 µs in both runs. Any deterioration against the M3 baseline is reported as an R5 finding, even if the thresholds are met.
9. No flash write at runtime is documented (what could write, and how it was disabled): §1.
10. Footprint reported; the LittleFS licence decision recorded (`docs/THIRD_PARTY_LICENSES.md`).

## 4. Bench procedure
1. **Credentials:** create `components/comms/include/wifi_credentials.h` from the template (see the top of this file).
2. **Flags:** `FE_M5_TEST` 1, `FE_M2_TEST`, `FE_M3_TEST` and `FE_M4_TEST` 0. The IMU is wired as for M3.
3. **Build:** `python3 tools/build_web.py`, `pio run`, `tools/verify_sdkconfig.sh`, `pio run -t buildfs`.
4. **Flash** (user): `pio run -t upload` (this also writes the partition table with the `readonly` flag), then `pio run -t uploadfs`.
5. **Monitor** from the project folder (the `log2file` filter keeps the log in `logs/`). Keep every device off the AP during M5-IMU-1 (300 s).
6. **External scan** on the laptop during M5-IMU-1, without joining: for example `nmcli -f SSID,CHAN,FREQ,SECURITY dev wifi list` or `sudo iw dev <wlan> scan`. Confirm channel 1 (2412 MHz) and WPA2. Do not paste the SSID into reports.
7. When the log prints `>>> join the laptop`, join the AP. When it prints `>>> start the load now`, run `python3 tools/m5_http_test.py --load 330`.
8. After the recap block: run `python3 tools/m5_http_test.py` (functional mode).
9. **Phone:** disconnect the laptop (one station maximum), join the phone, open http://192.168.4.1 and check the page and the version line. Then, with the phone joined, try to join the laptop or another device and write down what that device shows (investigation 3).
10. **Copy back:** the recap block, both client summary blocks, the scan line (without the SSID), the phone result, the second-device message, and any error or warning.

### 2. Settings that could reach Core 1 through Core 0 activity
- **Cache disable during flash operations** (both cores; Core 1 code in flash stalls, IRAM ISRs still run): flash writes and erases (none at runtime, §1) and flash reads through `esp_flash_read()` (LittleFS reads now go through the cache-mapped partition, D-M5-04). `CONFIG_ESP_PHY_INIT_DATA_IN_PARTITION` is off, so the PHY reads no partition at runtime.
- **Wi-Fi code from flash:** `CONFIG_ESP_WIFI_IRAM_OPT` and `CONFIG_ESP_WIFI_RX_IRAM_OPT` set (fewer cache misses on Core 0; they do not disable the cache). `CONFIG_ESP_WIFI_EXTRA_IRAM_OPT` and `CONFIG_LWIP_IRAM_OPTIMIZATION` are not set; candidates if M7 needs them.
- **PSRAM:** `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` is not set, so Wi-Fi and lwIP buffers stay in internal RAM.
- **Interrupt-off periods:** critical sections in the Wi-Fi driver and lwIP mask interrupts on Core 0 only. The Wi-Fi interrupt is allocated on Core 0 (Wi-Fi initialised from a Core 0 task). Core 1 can be affected only through the shared FreeRTOS kernel lock taken by task notifications (R5), which M5-IMU-1 and M5-IMU-2 measure.
- `CONFIG_SPI_FLASH_AUTO_SUSPEND` is not set (not needed with no runtime writes).

### 3. A second station when `max_connection` is 1
The soft-AP refuses the association and IDF raises no event for it (D-M5-09), so the firmware cannot log it. The refused device is expected to report a failed connection; the exact message is recorded at bench step 9.

**Notes.**
- **M5-IMU-2 load window.** The phone joined first (337 s) and its requests started M5-IMU-2 at 350 s; the laptop joined at 378 s and the client load began about 68 s into the run. M5-IMU-2 therefore had about 230 s under load. The loaded windows w08 onwards are the reference; the whole-run averages understate the load effect. The idle heap reference was taken with the phone joined, which is still a one-station reference.
- **IMU bus clear at boot.** `bus A lines before creation: SDA 0 SCL 1, SDA held low, cleared after 2 clocks, now SDA 1 SCL 1`, followed by a normal init (WHO_AM_I 0x70). A working check of the M4 bus-clear code (SDA held by a transaction cut off by a reset).
- **R5 finding.** Wake-up latency barely moves under load (max 22 µs against 12 µs in M3), so the kernel lock is not the main effect. The I2C burst read grows by about 160 µs (450 to 605–633 µs average). The I2C interrupt is already in IRAM (B-M5-07), so the likely cause is cache contention: Core 1 driver code running from flash while Core 0 serves Wi-Fi, LittleFS and PSRAM traffic. Recorded in blueprint §4.3 and §6.2 R5; measured again in M6, fixes considered in M7.
- **Footprint.** Free heap at boot fell by 62 580 B against M4; this matches the static growth (IRAM +33 280 B, which comes out of the shared SRAM, and DRAM data plus bss +24 748 B).

### Earlier failed run (31 October 2026, `logs/device-monitor-261031-200524.log`)
- The IMU failed at probe on every boot (`bus A lines before creation: SDA 0 SCL 0`), and the firmware crashed under HTTP load 7 times (cache error with MMU entry fault in `tlsf_malloc`, LoadProhibited and InstrFetchProhibited in the LittleFS read path, and 4 task-watchdog resets inside the panic handler). The dumps showed heap corruption near the start of PSRAM and in the VFS/LittleFS structures.
- After the wiring was checked, the identical firmware (ELF `96dcb5a16`) ran clean for 12.6 minutes under the same load. Cause recorded as **most likely the wiring fault (a loaded 3.3 V rail under Wi-Fi transmit peaks); not proven**.
- `CONFIG_LITTLEFS_MMAP_PARTITION` stays enabled and has not been isolated. If a crash recurs with good wiring, run the heap-poisoning test: `CONFIG_LITTLEFS_MMAP_PARTITION=n` as the isolation step, `CONFIG_HEAP_POISONING_COMPREHENSIVE=y` and a `heap_caps_check_integrity_all(true)` call from the Core 0 heap print.
